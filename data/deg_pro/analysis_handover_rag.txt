========================================
1. Purpose
========================================

This project builds a daily feature table for apparel sales analysis.
The main business intent is:

- Use JAN as the base SKU unit.
- Keep product_code so multiple JANs can be grouped as one product when needed.
- Correct raw daily sales so weekday bias and monthly/seasonal bias are reduced.
- Preserve zero-sales days because "not sold" is also meaningful for analysis.

Current main output:

- product_daily_features.csv

Current analysis notebook:

- product_daily_features分析.ipynb

Current feature-generation script:

- 補正プログラム.py

========================================
3. Current CSV Schema
========================================

Columns in product_daily_features.csv:

1. jan_code
- JAN code.
- Base SKU key.

2. product_code
- Product code.
- Used when multiple JANs should be grouped into one product.

3. sales_date
- Daily date.

4. sales_qty
- Raw daily sales quantity.

5. launch_date
- Launch/start date for the JAN.

6. day_of_week
- Monday=0 ... Sunday=6

7. month
- Month number 1-12

8. days_since_launch
- sales_date - launch_date in days

9. p99
- JAN-level 99th percentile cap used to soften large spikes

10. sales_qty_clean
- min(sales_qty, p99)

11. dow_index
- Shared weekday correction index

12. sales_dow_adj
- sales_qty_clean / dow_index

13. month_index
- Shared month correction index

14. sales_adj
- Final corrected sales
- sales_dow_adj / month_index
- Then capped so sold-day correction does not exceed 5x raw sales


========================================
4. Current Correction Logic
========================================

The latest logic in 補正プログラム.py is:

1. Read raw sales and mapping.
2. Merge sku_code with jan_code so each JAN gets a product_code.
3. Convert dates and numeric types.
4. Aggregate to JAN x date daily sales.
5. Fill missing dates from launch_date to global max date with sales_qty=0.
6. Add calendar columns:
   - day_of_week
   - month
   - days_since_launch
7. Build p99 from positive sales only.
8. Build sales_qty_clean = min(sales_qty, p99).
9. Build shared dow_index from all JANs.
10. Apply floor to dow_index so weekends are not over-amplified.
11. Re-normalize dow_index to mean 1.
12. Build sales_dow_adj = sales_qty_clean / dow_index.
13. Build shared month_index from JAN-level month ratios.
14. Re-normalize month_index to mean 1.
15. Build sales_adj = sales_dow_adj / month_index.
16. Cap sold-day correction so sales_adj <= sales_qty * 5.


========================================
5. Important Design Decisions
========================================

1. Base key is JAN, not product_code
- This is intentional.
- Daily rows are SKU/JAN-level.
- Product-level analysis should be done by grouping product_code later.

2. Zero-sales days are preserved
- This is intentional and important.
- The table is not only about sold days.
- Zero days are used to analyze demand sparsity and product lifecycle.

3. Weekday and month correction are shared, not SKU-specific
- dow_index and month_index are currently global/common rules.
- This was chosen for stable comparison across SKUs.
- p99 and launch-based fields are SKU-specific.

4. The current correction is for comparison, not "truth"
- sales_qty is actual observed daily sales.
- sales_adj is a comparison-friendly adjusted indicator.
- Do not replace operational raw sales reporting with sales_adj.


========================================
6. Current Parameter Values
========================================

From 補正プログラム.py:

- DOW_INDEX_FLOOR = 0.4
- MAX_CORRECTION_FACTOR = 5.0

Meaning:

- weekday indices cannot go below 0.4 before re-normalization
- sold-day corrected sales cannot exceed 5x raw sales


========================================
7. Problems Found Earlier And Fixes Already Applied
========================================

1. Problem: p99 could become 0 for sparse JANs
- Result: sold days could be incorrectly collapsed to 0
- Fix: p99 is now computed from positive-sales days only
- Extra safeguard: if a JAN has any positive sale, p99 is clipped to at least 1

2. Problem: weekend correction was too strong
- Result: Saturday/Sunday corrected sales were amplified too much
- Fix: weekday index floor added and re-normalized

3. Problem: month_index was globally below 1
- Result: corrected sales were being pushed up too broadly
- Fix: month_index is now normalized to mean 1

4. Problem: extreme adjusted values still possible
- Fix: sales_adj on sold days is capped at raw sales * 5

11. How To Use The Data Correctly
========================================

Use sales_qty when:

- checking actual operational sales
- reporting observed daily sales
- looking at true raw demand realization

Use sales_adj when:

- comparing SKUs under more equalized conditions
- comparing product-level strength
- checking lifecycle patterns while reducing weekday/month effects

Use product_code grouping when:

- a product is represented by multiple JANs
- comparing products instead of SKUs

Use jan_code when:

- analyzing individual SKU behavior
- comparing sizes/colors/SKU-specific demand


========================================
12. What Is Already Understood Conceptually
========================================

The following concepts were already discussed and should be preserved:

1. p99 is percentile, not statistical confidence
- It is a distribution cutoff, not "95% confidence"

2. Weekday correction and month correction are similar in spirit
- both build an index and divide by it
- but month correction is more careful:
  it first builds JAN-level month ratios, then aggregates them

3. Zero-sales days are important
- they are not noise
- they are part of the signal

4. Shared correction is intentional
- current weekday and month indices are not SKU-specific
- that is a deliberate tradeoff for comparability and stability


========================================
13. Current Risks / Limits
========================================

These are known limitations of the current approach:

1. Shared weekday/month correction may miss SKU-specific seasonality
- especially if certain motorcycle products behave differently from general apparel

2. Zero-heavy data
- around 93% of daily rows are zero-sales rows
- this is not wrong, but it affects interpretation and future modeling

3. Filled date ranges favor long-lived JANs
- older or long-selling JANs contribute more rows
- this can bias aggregate analyses unless grouped carefully

4. No stockout / availability flag exists
- zero sales may mean "no demand" or "not available"
- this is not distinguishable in the current table
